# StudyRoom AI 기능 검토 (2026-09-06)

상태: 기능 후보 검토 완료. 구현 승인 또는 확정 PRD가 아니다. 실제 사용자 기록·API 키를 조회하거나 모델을 호출하지 않았다.

## 현재 코드에서 확인한 기반

- main.tsx의 StudyGoal/StudyTodo/StudySession/StudySessionReflection: 목표 날짜/상태, 할 일 제목/날짜/시간/목표 연결, 세션 시간, 집중·에너지 점수/방해 사유/회고 메모/다음 행동이 있다.
- dashboardData.ts: 목표·할 일·세션 및 별도 회고 조회가 있다. 기존 클라이언트 조회를 AI 서버 권한 검증 대신 신뢰해서는 안 된다.
- weeklyReview.mjs 및 WeeklyReviewSection.tsx: 같은 요일 범위의 전주 비교, 통계, 방해 사유별 고정 조언, 다음 행동을 할 일 계획으로 연결하는 기능이 이미 있다.
- adaptiveReminder.mjs: 최근 완료 세션의 첫 시작 시각 중앙값으로 알림을 추천한다. 이를 AI 신기능으로 재포장할 필요 없다.
- GoalAchievementBadges.tsx: 완료 목표 배지가 있다. 목표 달성 여부는 사용자/저장 상태가 결정한다.
- server/ai/openrouter.mjs: 서버 전용 텍스트 호출 모듈만 있음. 앱 호출 지점/공개 AI route/구조화 출력 계약/사용자별 사용량 통제는 아직 없다. vercel.json은 SPA catch-all이다.
- 동적 라우팅 수정은 미커밋 상태이며 이전 자동 승인 검토로 배포가 차단되어 있다. 이번 검토는 그 승인이나 실제 운영 호출 성공을 의미하지 않는다.

## 후보와 우선순위

| 순위 | 기능/진입 화면 | AI가 더하는 가치 | 필요한 데이터/추가 입력 | 상대 규모 |
| --- | --- | --- | --- | --- |
| 1 | 마이페이지 주간 리뷰의 AI 코치 | 회고 메모와 미완료 할 일 맥락을 읽고 근거 있는 다음 행동 1~3개 제안 | 기존 주간 요약/회고/할 일. 기록 부족 시 개인화 결론 보류 | 중 |
| 2 | 목표 화면의 학습 계획 초안 | 큰 목표를 실행 가능한 할 일로 분해 | 목표/기한 외 공부 범위·현재 수준·주당 가능 시간·자료 목차 입력 필요 | 중~대 |
| 3 | Today/할 일 추가의 자연어 입력 | '내일 저녁 8시부터 50분 AWS 복습'을 제목/날짜/시각 필드로 변환 | 사용자 문장, 기준 날짜/시간대, 목표 후보. 모호한 시간은 질문 | 중 |
| 4 | Today의 오늘 계획 조정 | 남은 시간·우선순위에 맞게 미완료 할 일 축소/분할 제안 | 기존 일정 외 가용 시간·중요도·예상 소요 입력 필요 | 중~대 |
| 5 | 세션 회고의 다음 행동 도우미 | '진도가 막혔다' 같은 메모를 다음 세션 첫 행동으로 구체화 | 이번 세션 할 일/메모, 사용자 선택. 매 종료마다 호출하지 않음 | 소~중 |
| 6 | 자료 기반 복습 퀴즈/오답 설명 | 제공 자료에서 문제/해설·복습 계획 생성 | 노트/자료 수집, 출처/범위, 정답 검증, 오답 이력 저장 새로 필요 | 대 |

규모는 공통 API 기반을 제외한 상대 비교이며 개발 일정 약속이 아니다. 1→2→3 순서를 기본 제안하며 빠른 입력 편의가 최우선이면 3을 앞당길 수 있다.

## 권장 첫 출시: 주간 AI 코치

사용 흐름: 마이페이지 → 기존 주간 리뷰 → 'AI 코칭 받기' → 잘한 점 1개/다음 시도 최대3개/각 제안의 근거 표시 → 사용자가 선택한 행동만 기존 할 일 계획 폼으로 이동 → 날짜·시간 확인 후 저장.

숫자는 기존 코드/서버 집계로 계산하고 AI에는 집계 결과와 필요한 메모만 전달한다. 예를 들어 여러 회고에 피로가 기록되었다면 더 짧은 첫 세션을 제안할 수 있으나 피로가 공부 감소의 원인이라고 확정하지 않는다. 샘플 수·비교 기간을 표시하고 데이터가 적으면 일반 제안임을 밝힌다.

- 기본은 클릭 요청. 회고 저장/페이지 방문마다 생성하지 않는다.
- 동일 사용자·기간·입력 버전·모델 정책/프롬프트 버전의 결과를 재사용한다. 기록 변경/삭제 시 무효화한다.
- 기존 통계와 회고 저장은 AI 실패/timeout과 독립적으로 작동한다.
- 사용자별 사용량 제한과 생성 ID/실제 모델/토큰/상태 기록, 결과 삭제 정책을 설계한다.
- 출시 지표: 제안의 할 일 전환율, 전환된 할 일 완료율, 유용성 평가, 응답 지연/실패율/활성 사용자당 비용. 실제 값과 향상률은 출시 전 알 수 없다.
- 수용 기준: 타인 기록 차단, 숫자 근거 일치, 존재하지 않는 기록 인용 거부, 사용자 확인 없는 일정 변경 금지, 연속 클릭 중복 생성/저장 방지, AI 실패 시 기존 리뷰 이용 가능.

## 구현 전 공통 준비

1. 인증된 서버 API와 사용자 소유 데이터 조회, SPA /api 라우팅, 서버 키 실행환경을 연결하고 실제 연동을 검증한다.
2. 목적별 최소 데이터만 전달한다. 카메라 영상/계정 이메일/전체 생활 기록은 이 후보들에 불필요하다. 회고 메모의 외부 AI 처리 안내와 제공자 데이터 정책을 확인한다.
3. 텍스트 전용 client를 스키마 기반 결과 생성으로 확장한다. 날짜/시간 충돌·가능 시간·할 일 ID·권한·중복 저장은 일반 코드로 검증한다. AI에 DB 수정 권한을 직접 주지 않는다.
4. 모델은 한국어 제안 품질·근거 정확성·JSON 준수·지연·비용으로 평가한다. 자연어 필드 추출과 긴 목표 계획은 다른 요구이므로 auto만으로 품질 검증을 대체하지 않는다.
5. 현재 기본 1024토큰/20초는 짧은 코칭에는 시작점이지만 긴 계획에는 평가 후 조정한다. cost tier는 지출 한도가 아니므로 별도 예산 통제가 필요하다.

OpenRouter 구조화 출력은 endpoint별 지원 확인과 response_format/json_schema, provider.require_parameters가 필요하다. 현재 client에는 해당 파라미터 통로가 없으므로 기능 추가 작업에 포함한다. 스키마 준수도 내용의 사실성을 보장하지 않는다.

## AI를 붙이지 않을 부분

출석 판정, 공부 시간/완료율/D-day 계산, 시간 겹침 판정, 목표 완료·삭제·배지 지급, 반복 일정 생성 규칙은 기존 결정적 코드로 유지한다. 개인화 동기부여 문구만 추가하는 기능은 반복 사용 가치가 낮아 후순위다. 범용 챗봇과 자료 없는 시험문제 생성은 제품 적합성/근거 부족으로 첫 출시에서 제외한다.
