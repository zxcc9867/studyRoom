# 자리비움 회복 요청 재생성 분석

## 범위
- 사용자 요청은 원인 분석과 UX 대안이다. 판정·회복 정책/운영 함수/학습 기록은 변경하지 않는다.
- 분석 시점 learning-continuity UI는 checkpoint로 보존했다. 이후 사용자가 별도로 재개를 승인하여 구현·검증을 완료했으며 최신 출시 상태는 [continuity 검증](2026-11-05-learning-continuity.md)을 따른다. 이 분석의 회복·카메라 개선안은 사용자 선택으로 보류한다.
- 운영 제품75ab1da, camera-presence-warning Edge24/ACTIVE와 실제 DB 함수 정의를 읽기 전용으로 확인했다. 실계정 테스트 쓰기/카메라/앱 재로드 없음. 계정 ID·이메일·사유 원문·학습 내용·원시 이벤트는 문서에 남기지 않는다.

## 확인한 원인
1. 결석(missed_attendance)과 카메라 반복(camera_absence_repeat)은 별도 요청이다. 그러나 이번 사례는 같은 공부일·같은 camera 유형의 제출 완료 뒤 새 pending이 생긴 경우였다. 제출 실패나 결석 요청의 재개방이 아니다.
2. public.claim_study_camera_warning는 해당 공부일의 absence_warning 행 수를 누적한다. 제출 시점 이후 또는 독립 미감지 구간 수가 아니다. Edge24는 누적>=3일 때 회복 생성 helper를 호출한다.
3. 배포된 helper의 loadPendingRecoveryRequest는 status=pending만 찾는다. 같은 날짜·유형의 submitted는 재사용/제외하지 않는다. DB unique index도 pending만 제한하므로 다음 경고에서 새 pending을 만들 수 있다.
4. cameraPresence는 연속 미감지5분 경고 후10분 cooldown마다 다시 경고한다. 동일 구간의5분·15분 경고를 각각 세므로 경고3회는 독립 자리비움3회가 아니다. 실제 기록에서도 같은 연속 미감지의 반복 경고가 확인됐다.
5. 새 요청은 공부 종료 전에 생성됐다. 운영 main의 endTimer→loadDashboard→pending 자동 열기 경로로 종료 뒤 보일 수 있다. 경고 client는 recoveryResult를 화면 state로 전달하지 않아 생성 시각/제출 완료 여부가 사용자에게 드러나지 않는다. 종료 자체가 카메라 회복을 생성하는 것은 아니다.

## 미확정 부분
- 서버 기록은 담당 기기의 상반신 미감지 보고이며 실제 물리적 자리비움의 증거는 아니다. 각 세션 경고의 담당 세대/클라이언트는 하나였다. 이번 자료에서 관찰 기기의 중복 경고 근거는 없다.
- 현재 판정은 기존 머리+양어깨 또는 머리+같은쪽 어깨·골반 조건이다. 자세/crop/조명/낮은 confidence로 실패할 수 있으나 당시 어느 조건이 실패했는지는 기록하지 않는다.
- 원영상·프레임·랜드마크는 저장/전송하지 않아 과거 자세를 재구성하거나 오탐률을 산출할 수 없다. 감지 민감도·GPU/카메라 고장 원인을 확정하지 않는다.
- 검은 화면/끊긴 트랙/프레임 미준비는 코드상 별도 health 오류로 reset한다. 이 코드 확인을 실기기 영상 정지의 완전한 배제로 확대하지 않는다.

## 합성 재현과 기존 검사
- cameraPresence를 직접 호출: 한 번의 연속 미감지에서5/15/25분 모두 warningDue=true, absenceStartedAtMs는 동일했다. 실계정 데이터는 사용하지 않았다.
- `node --test apps/web/test/cameraPresence.test.mjs apps/web/test/upperBodyPresence.test.mjs apps/web/test/cameraVideoHealth.test.mjs`:24/24 pass, fail/skip/cancel0, exit0.
- 이 결과는 현재 정책의 동작 확인이지 오탐이 없다는 인증이나 수정 완료가 아니다. 제품 파일은 기존 운영75ab1da와 같으며 새 continuity UI diff와 분리했다.

## UX 대안 (미승인 제안)
- A. 같은 공부일·유형은 제출 후 다시 강제하지 않기: 감사 이력/경고는 유지하되 회복 작성 중복을 막는다. 권장 기본안.
- B. 경고 횟수가 아니라 독립 미감지 구간3회로 집계: 정상 감지가 안정적으로 복구된 뒤에만 다음 구간으로 센다. 반복 Slack 알림은 같은 구간의 안내일 뿐 별도 횟수가 아니다.
- C. 제출 이후 새 구간3회를 별도 기준으로 재요청: A보다 엄격하지만 같은 날 반복 작성 부담이 남는다. 기본안으로 권장하지 않는다.
- D. 카메라 감지 확인을 결석 보충 양식과 분리: 실제 휴식/앉아 있었음/연결 문제의 짧은 확인을 먼저 제공한다. 기술 문제 응답만으로 과거 인정시간을 자동 복구하지 않는다.
- E. 로컬 감지 진단·촬영 구도 확인: 머리/어깨/골반/프레임 상태를 기기 안에서만 표시하고 저장하지 않는다. 기존 판정 기준을 바꾸지 않고 원인 수집을 돕는다.
- F. 진행 중 공부를 강제 종료하지 않는 사후 확인: 종료 후 요약과 접힌 감지 내역을 보여주고 명시적으로 확인한다. 현재 blocker/자동 종료 정책과 충돌하므로 별도 승인 필요.
- 추천: A+B를 우선 검토하고 D+E로 설명/오탐 신고 UX를 보완한다. threshold5분/10분과 기존 상반신 조건은 현재 사용자 결정대로 유지한다. 중복 pending 정리는 승인 후 원인을 남겨 resolved 처리하는 방안을 검토하며 삭제·과거 시간 재정산은 하지 않는다.
