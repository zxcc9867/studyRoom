STUDY ROOM / AWS CDK / REVIEW DRAFT

독서실 AWS 아키텍처 리뷰

기존 혼합형과 Aurora 기반 AWS 완결형의 서비스 역할·운영 차이·예상 비용을 비교합니다. 배포 전 설계 초안입니다.

한눈에 보기 1 · 혼합형2 · Aurora 완결형서비스 역할 운영 비교월 예상 비용이전 검토선택 기준

현재 권장: 작은 독서실의 비용과 전환 위험을 줄이는 데는 혼합형이 유리합니다. Aurora 완결형은 Supabase·OpenRouter를 제거하고, AWS 안에서 인증·DB·모델·복구를 관리해야 할 때 검토하는 안입니다.

AT A GLANCE / SAME APP, TWO OWNERSHIP MODELS

무엇이 어디에서 실행되나요?

두 안 모두 사용자는 같은 독서실 화면을 봅니다. 차이는 화면 뒤에서 로그인, 학습 기록, 실시간 알림, AI를 누가 맡느냐입니다. 어느 안도 아직 운영에 적용되지 않았습니다.

1 · 화면과 코칭 입구만 옮기기

  1. 화면 열기CloudFront가 비공개 S3에서 화면을 가져옵니다.
  2. 로그인·기록·실시간 갱신앱이 지금처럼 Supabase에 연결합니다.
  3. AI 코칭API Gateway → Lambda → OpenRouter. 기존 코칭 흐름을 최대한 유지합니다.

왜? 학습 기록을 옮기지 않고 AWS 배포부터 검증할 수 있습니다.

2 · 인증·DB·AI까지 AWS에서 운영

  1. 화면 열기·로그인CloudFront·S3는 그대로, 로그인은 Cognito로 바뀝니다.
  2. 저장·갱신Lambda가 Aurora에 저장하고 AppSync가 열린 앱에 변경을 알립니다.
  3. AI 코칭접수 → SQS → Lambda 워커 → Bedrock. 완료 후 결과를 조회합니다.

왜? 외부 데이터·AI 플랫폼을 제거하고 AWS 안에서 복구와 권한을 설계할 수 있습니다.

01 / BASELINE

구성도 1 · AWS + Supabase + OpenRouter

CloudFront·S3에 화면을, API Gateway·Lambda에 코칭 API를 옮기되 인증·DB·실시간·정기 작업은 Supabase에, 모델 호출은 OpenRouter에 남깁니다.

좁은 화면에서는 구성도를 좌우로 스크롤할 수 있습니다.

왜 이 방식인가

기존 로그인과 학습 기록을 건드리지 않고 Vercel 밖에서 앱을 실행할 수 있는지 먼저 검증합니다. 현재 50초 코칭 경로는 Regional REST API 시간 한도 상향과 CloudFront 대기 시간을 사전에 확인합니다.

대신 남는 것

Supabase·OpenRouter 장애의 영향은 그대로입니다. 현재 설치 앱은 기존 Vercel 주소를 신뢰하므로 AWS 배포만으로 접속 주소가 바뀌지는 않습니다.

02 / AWS-NATIVE / ELASTIC CAPACITY

구성도 2 · Aurora PostgreSQL + Bedrock

DB 사용량 편차가 크거나, 다른 가용 영역의 읽기 인스턴스로 장애 전환할 운영 구조가 필요한 경우의 후보입니다.

좁은 화면에서는 구성도를 좌우로 스크롤할 수 있습니다.

왜 Aurora Serverless v2인가

설정한 최소·최대 ACU 범위에서 DB 컴퓨팅 용량을 조정합니다. 운영안에는 Writer와 다른 AZ의 Reader를 두어 장애 전환 대상을 확보합니다. 읽기 분산은 필요한 쿼리에만 적용하고, 세션·정산처럼 최신성이 필요한 경로는 Writer 기준으로 유지합니다.

무엇을 검증해야 하나

Writer·Reader의 ACU, 스토리지·I/O, RDS Proxy를 합산해야 합니다. 반복되는 상태 갱신과 연결 풀을 고려해 0 ACU 일시중지나 무료 운영을 가정하지 않습니다. 장애 전환 중 쓰기 재시도와 중복 방지를 시험합니다.

SERVICE GUIDE

서비스별 역할

AppSync Events는 ‘공부 상태가 바뀌었다’고 알려줍니다

PC에서 공부를 시작하면 Lambda가 Aurora에 ‘공부 중’을 저장합니다. 저장이 끝나면 서버가 AppSync에 “상태가 바뀌었어요”라는 신호를 보냅니다. 같은 계정의 휴대폰이나 권한 있는 팀원 화면은 WebSocket 연결로 신호를 받아 API에서 최신 상태를 다시 읽습니다.

AppSync는 시간을 재거나 기록을 저장하지 않고, 카메라 영상도 보내지 않습니다. 신호를 놓치면 재연결·화면 복귀·열린 화면의 주기적 보조 조회로 상태를 다시 확인합니다. 구성도 1에서는 Supabase Realtime이 변경을 알려줍니다. 구성도 2에서는 구독과 API 조회 양쪽에서 팀원 권한을 검사합니다.

서비스·경계구성도 1 · 혼합형구성도 2 · Aurora 완결형
CloudFront / S3CloudFront는 HTTPS 접속 주소이자 화면·배경 영상의 CDN입니다. S3는 빌드 파일을 담는 비공개 저장소이고, OAC를 사용해 CloudFront에 원본 읽기 권한을 줍니다.
API GatewayRegional REST API가 기존 코칭 요청을 받습니다. 최대 50초의 기존 흐름을 유지하려면 시간 한도 상향과 CloudFront 대기 시간 검증이 필요합니다.HTTP API가 공부 기록·할 일·팀·코칭 요청을 받고 JWT를 검증합니다. 긴 AI 요청은 접수 후 결과를 따로 돌려줍니다.
LambdaVercel에서 옮긴 코칭 함수가 기존 로그인 검증과 OpenRouter 호출을 수행합니다.API와 백그라운드 워커를 실행합니다. 권한·공부 규칙을 검증하고 DB 저장, 이벤트 발행, AI 작업을 처리합니다.
인증Supabase Auth가 기존 계정·로그인·토큰을 유지합니다.Cognito User Pool이 로그인과 토큰을 담당합니다. 기존 사용자 ID와 새 인증 ID를 안전하게 매핑해야 합니다.
DB / 연결Supabase PostgreSQL에 학습 기록을 저장하고 RLS와 RPC가 접근·저장 규칙을 적용합니다.Aurora PostgreSQL이 기록의 원본입니다. RDS Proxy는 Lambda의 DB 연결을 재사용하는 통로이며, 별도의 RDS DB가 아닙니다. 기존 권한 정책과 SQL 함수 이식이 필요합니다.
실시간 전달Supabase Realtime이 DB 상태 변경을 열린 화면에 알립니다.AppSync Events가 서버의 갱신 신호를 개인·팀 채널에 전달합니다. 실제 조회·저장은 인증된 API가 담당합니다.
정기 작업 / 대기열Supabase Cron·Edge Functions가 출석·회복·알림·기술 피드 등 기존 작업을 처리합니다.EventBridge Scheduler는 언제 실행할지 정합니다. SQS는 아직 처리되지 않은 작업을 보관하고 Lambda 워커가 가져갑니다.
AI 모델OpenRouter가 코칭·요약을 기존 모델에 전달합니다.Bedrock에서 모델을 호출하고 IAM으로 호출 권한을 관리합니다. 응답 품질과 비용은 모델별로 확인합니다.
네트워크코칭 함수는 Supabase·OpenRouter에 HTTPS로 접속합니다. 이 제안은 전용 VPC/NAT를 두지 않습니다.Lambda·Proxy·DB는 VPC 사설 연결을 사용합니다. NAT는 Slack·RSS 등 외부 HTTPS 호출을 위한 송신 경로입니다.
IAM / Secrets Manager / CloudWatchIAM은 AWS 자원 접근 권한을, Secrets Manager는 서버 전용 키·자격 증명을, CloudWatch는 오류·지연·작업 실패의 로그와 알람을 담당합니다.
AWS CDKAWS 자원을 코드로 정의하고 환경별로 재현합니다. 기존 데이터나 로그인 세션을 자동으로 옮기지는 않습니다.

DECISION / HYBRID VS AWS-NATIVE

구성도 1과 2 비교

평가 기준1 · 혼합형2 · Aurora 완결형
비용 효율소규모에서 유리합니다. 전용 Aurora·Proxy·NAT 고정비가 없고 Supabase 플랜과 OpenRouter 사용료가 변수가 됩니다.적은 사용량에도 Writer·Reader와 NAT가 계속 과금됩니다. 피크 DB 사용량까지 늘면 실측한 ACU로 다시 계산해야 합니다.
운영 효율기존 인증·동기화·스케줄을 재사용해 출시 부담이 작습니다. 장애 원인은 AWS·Supabase·OpenRouter 각각에서 확인해야 합니다.AWS 권한·지표·배포를 한곳에서 관리할 수 있습니다. 대신 큐·구독 권한·네트워크·백업 복구를 직접 운영해야 합니다. Google·Slack 등 외부 연동은 남습니다.
이전 부담화면과 코칭 함수가 주 범위입니다. 학습 기록과 기존 계정은 옮기지 않습니다.계정 매핑과 데이터, 기존 RLS·RPC·Edge Functions·Realtime 동작을 이식하고, 데이터 정합성과 되돌리기를 검증해야 합니다.
성능·확장기존 Supabase 한도와 외부 모델 응답 시간의 영향을 받습니다. 소규모에서는 구조를 바꿀 이점이 작습니다.Aurora는 설정 범위에서 DB 용량을 조절하고 SQS로 AI 부하를 분리합니다. 큐 대기·추가 조회가 생겨 모든 요청이 더 빨라지는 것은 아닙니다.
장애·복구외부 공급자의 장애와 백업 범위에 의존합니다. 기존 운영을 보존한 채 시험 주소에서 검증하기 쉽습니다.다른 가용 영역의 Reader로 DB 장애 전환을 설계할 수 있습니다. DB Multi-AZ는 전체 앱 무중단이나 리전 장애 대응을 보장하지 않습니다.
보안·통제검증된 기존 정책을 유지하되 공급자별 접근 정책과 로그를 살펴야 합니다.DB 사설 접속과 모델 호출 IAM을 직접 통제할 수 있습니다. 권한 이식 누락과 팀 구독 데이터 노출도 직접 검증해야 합니다.

선택 기준: 낮은 비용과 빠른 이전이 우선이면 1안, 외부 데이터·AI 플랫폼 의존 제거와 AWS 안에서의 통제가 월 고정비 및 이식 부담보다 중요하면 2안입니다.

  • Aurora: 두 인스턴스가 평균 0.5 ACU씩이라는 저부하 가정입니다. 합산 평균이 1 ACU 더 늘면 Aurora + Proxy가 월 $164.25 추가됩니다. Proxy가 연결을 유지하는 이 구성에는 0 ACU 자동 일시중지를 적용하지 않았습니다.
  • NAT: 1개로 줄인 가정은 월 약 $216.65이지만, 송신 경로의 AZ 이중화를 잃고 교차 AZ 전송비가 생길 수 있습니다. VPC 외부로 통신하는 작업만 분리해 NAT를 대체할 수 있는지는 네트워크와 비용을 다시 설계해야 합니다.
  • AppSync: 50만 회는 발행·전달·연결·구독·핑·핸들러를 합한 예시입니다. API 보조 조회는 별도입니다. 예를 들어 연결 12만 분 전부에 현재의 15초 주기를 그대로 적용하면 보조 조회만 120000 × 60 ÷ 15 = 480000건이므로 10만 API 가정을 다시 잡아야 합니다.
  • Bedrock: 서울 호출 기준 Nova Micro의 공개 단가를 사용했습니다. 서울에서 이 모델을 호출할 때는 지역 간 추론 프로필 지원을 확인해야 하며, 서울 안에서만 처리된다고 가정할 수 없습니다. 한국어 품질 검증 후 모델이 달라지면 AI 비용도 다시 계산합니다.

가정·제외: CloudFront와 Cognito의 명시한 상시 무료 구간 외에 신규 계정 크레딧, 기간 한정 무료 혜택, 예약 할인은 적용하지 않았습니다. 도메인·DNS·WAF·별도 KMS 키·추가 백업·유료 VPC 엔드포인트·이메일/SMS·교차 AZ 또는 인터넷 전송 추가분·세금·마이그레이션/운영 인건비는 포함하지 않았습니다. 기존 Vercel과 AWS를 동시에 운영하는 기간의 중복 비용도 별도입니다. 행은 반올림하고 합계는 반올림 전 금액을 더했습니다.

MIGRATION / REVIEW GATES

Supabase와 OpenRouter를 빼면 다시 만들어야 하는 것

인증과 권한 — Cognito + 서버 API

Cognito User Pool이 로그인과 토큰을 담당하고 API Gateway가 JWT를 검증합니다. 앱은 DB에 직접 연결하지 않습니다. 기존 사용자 UUID는 학습 기록의 키로 유지하고, 검증된 Cognito sub를 그 UUID에 매핑합니다. 이메일 문자열만 보고 기존 계정에 연결하지 않습니다. Google·이메일 로그인, Windows·Android PKCE와 복귀 주소는 새 흐름으로 검증하고, GitHub 로그인은 지원 방식부터 따로 확인합니다.

토큰 확인만으로 팀 접근이 허용되지는 않습니다. Lambda에서 사용자·팀별 권한을 검증하고, 기존 auth.uid()를 사용하는 DB 정책과 RPC는 새 인증 주체에 맞춰 이식합니다. 마이그레이션용 관리자 권한과 런타임 권한은 분리합니다.

실시간 상태 — AppSync Events

기기·팀별 채널에 DB 저장 성공 뒤 변경 신호를 발행합니다. 구독 때 멤버십을 검증하고, 탈퇴·권한 변경과 재연결을 별도로 검증합니다. 이벤트에는 개인 학습 내용이나 카메라 영상을 담지 않습니다. 신호 유실을 대비해 최신 상태를 인증된 API에서 다시 읽으며, 열린 화면에서의 보조 조회 주기는 허용 지연과 비용을 함께 측정해 정합니다.

AI — SQS + Lambda 워커 + Bedrock

Bedrock은 OpenRouter의 외부 API 키 대신 AWS IAM 권한으로 모델 호출을 관리할 수 있어 완결형에 넣었습니다. 코칭·요약에 필요한 모델만 허용하고, 기존 무료 모델과 같은 요금·결과를 보장하지 않습니다.

현재 코칭 핸들러는 최대 50초를 허용하지만 HTTP API 한도는 30초입니다. 완결형은 POST 요청에서 작업을 접수해 202와 작업 ID를 반환하고, 워커가 Bedrock으로 생성한 결과를 앱에서 조회하도록 설계했습니다. 기존 동기 응답을 바꾸는 설계이므로 UI의 대기·실패·재시도 상태도 검증해야 합니다. DB에 작업과 발행 대상을 같은 트랜잭션으로 기록하는 패턴(outbox), 중복 방지 키, 실패 대기열을 둡니다. Bedrock 모델·리전 가용성, 한국어 품질, 호출 비용·데이터 처리 조건은 시험 후 확정합니다.

정기 작업과 네트워크 — EventBridge Scheduler + 작업 워커

출석·회복·Slack 알림·기술 피드의 정기 작업은 스케줄러와 워커로 옮기고, 중복 실행에도 기록이 한 번만 반영되도록 합니다. DB와 Proxy는 비공개로 유지합니다. RDS Proxy는 여러 Lambda 실행에서 DB 연결을 재사용하기 위한 후보로, 실제 연결 재사용 효과와 동시 실행 상한을 함께 검증합니다. Bedrock 등 지원 서비스는 VPC 엔드포인트를 검토하고, Slack·RSS처럼 인터넷 연결이 필요한 호출은 제한된 송신 경로를 사용합니다.

‘완결형’의 범위: Supabase와 OpenRouter 없이 앱을 운영한다는 뜻입니다. Google 로그인, Slack, RSS 원문은 기능을 유지하는 한 외부입니다. 기존 DeepL 번역까지 없애려면 Bedrock 등으로 별도 대체하고 번역 품질·비용을 확인해야 합니다.

운영 전환 전에 통과할 기준

  1. 시험 계정·합성 데이터로 로그인, 출석·회복, PC·모바일 동기화, 팀 권한, 정기 작업의 기존 동작을 재현합니다.
  2. PostgreSQL 버전·확장·트리거·RLS·RPC 호환성을 검증합니다. 시험 복원본으로 행 수·제약·샘플 정산을 비교하고, 실제 데이터 이전과 보존 검증은 별도 승인을 받습니다.
  3. 피크 부하, DB 장애 전환, 백업 시점 복구, 알림 중복, Bedrock 응답 지연을 시험해 비용과 복구 목표를 비교합니다. 구·신 시스템이 같은 기록을 동시에 쓰는 전환은 피하고, 신규 쓰기가 시작된 뒤의 복귀 방법도 미리 정합니다.
  4. 전환이 승인되면 도메인·로그인 복귀·설치 앱의 신뢰 주소·APK 업데이트 경로를 함께 검증합니다. AWS CDK 배포가 데이터 이전이나 기존 로그인 세션 이전을 대신하지 않습니다.

GO / NO-GO

무엇을 확인하고 결정하나요?

  1. 비용: 한 달치 실제 Supabase·OpenRouter 사용량과 CDN 전송량을 읽기 전용으로 집계한 뒤, 월 예산과 비교합니다. 이 문서의 금액은 사용자 청구액이 아닌 예시입니다.
  2. 성능: 동일한 기기·리전·테스트 데이터로 화면 로딩, 일반 API 응답(p95), PC에서 상태를 바꾼 뒤 모바일에 표시되는 시간(p95), AI 요청 접수·완료 시간을 각각 측정합니다. 현재 어느 안도 실측 우위를 확인하지 않았습니다.
  3. 복구: 허용할 데이터 손실(RPO)과 서비스 복구 시간(RTO)을 먼저 정합니다. 완결형은 Aurora 장애 전환, 큐 중복 처리, 백업 시점 복원, 팀 권한 차단을 시험합니다.
  4. 전환: 지금 목적이 낮은 비용과 AWS 배포 검증이라면 1안을 먼저 시험합니다. 외부 데이터·AI 플랫폼 제거가 필수이고, 2안이 월 예산·성능·복구 기준을 모두 통과하면 완결형으로 넘어갑니다.

리뷰에서 정할 것: 월 비용 상한, Supabase·OpenRouter 제거 필요성, 허용 지연과 복구 목표. 이 문서는 선택을 위한 제안이며 리소스 생성·데이터 이전의 승인이 아닙니다.
