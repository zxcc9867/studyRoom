# Windows 독서실 앱 설계 — A 방식

- 작성: 2026-10-24
- 상태: 2026-10-25 서면 설계 승인·구현 진행. 설치·운영 설정 변경은 별도 검증 상태를 따른다.
- 요구사항 정본: [Windows PRD](../../../memory-bank/prd-windows-desktop.md)

## 1. 사용자에게 보이는 결과

기존 독서실을 Windows 시작 메뉴와 바탕화면에서 여는 설치형 앱으로 제공한다. 내부 화면은 기존 Vercel 웹앱을 재사용한다. 별도 대시보드나 학습 DB를 만들지 않으며, 같은 계정의 웹·Android·Windows가 같은 학습 기록을 조회한다. 목업의 새 원형 타이머는 채택하지 않는다.

사용자가 승인한 A 방식은 다음과 같다.

- 제목 표시줄의 X는 창을 트레이로 숨긴다. 창과 웹 문서를 파괴하거나 새로 불러오지 않는다.
- 숨김 자체는 공부 종료·휴식·카메라 해제·담당권 이전을 요청하지 않는다. 켜 둔 카메라와 공부를 유지한다.
- 트레이에서 현재 상태를 확인하고 창을 다시 연다. 앱을 완전히 종료하는 메뉴는 별도로 둔다.
- 공부 종료·회복·카메라 담당·출석 계산은 기존 웹과 서버 정책을 그대로 따른다.

인터넷은 계속 필요하다. 트레이 실행은 Windows 절전·컴퓨터 종료·카메라 물리 차단·네트워크 단절까지 해결하는 기능이 아니다. 시스템 절전 정책이나 자동 시작 설정을 임의로 변경하지 않는다.

## 2. 구조와 상태 소유권

Electron을 얇은 Windows 셸로 사용하고 `https://study-room-attendance.vercel.app`의 기존 화면을 하나의 BrowserWindow에 로드한다. 초기 지원은 Windows 10/11 x64다. 실제 지원 판정은 선택한 Electron의 공식 지원 범위와 빌드·실행 검증 결과를 따른다.

| 구성 요소 | 소유하는 상태·책임 | 소유하지 않는 것 |
|---|---|---|
| `apps/desktop` main | 창·트레이·단일 인스턴스·네이티브 인증·암호화 저장·권한·외부 링크·종료 요청 | 공부 시간·출석·할 일·카메라 판정 |
| desktop preload | 검증된 좁은 브리지와 응답 전달 | Node API·임의 IPC·파일·프로세스 실행 |
| 기존 웹 DashboardApp | 공부 시작·휴식·재개·종료·회고·카메라 및 기기 참여 상태 | Windows 프로세스 관리 |
| Supabase | 인증 확인·학습 기록·동일 계정 세션·카메라 담당·인정 시간 | Windows 창의 표시 여부 |

새 코드는 `apps/desktop` workspace에 한정한다. main/preload 진입점은 `.cjs`, 테스트 가능한 순수 정책·상태 전이는 작은 `.mjs` 모듈로 분리한다. 웹에는 독립적인 desktop 브리지와 인증 게이트, 플랫폼별 설정 표시만 추가한다. 웹에서 desktop/main 또는 서버 구현을 직접 import하지 않는다.

Android의 `ReactNativeWebView`를 흉내 내지 않는다. Windows는 별도 `window.studyRoomDesktop` capability를 사용한다. 기존 서버 카메라 기기 종류는 `browser` 계약을 재사용하고, Windows 표시만 클라이언트에서 구분한다. 새 DB 종류·테이블·마이그레이션은 이 범위에 필요하지 않다.

## 3. 창·트레이 동작

### 실행과 복원

- 기존 독서실 아이콘을 창·작업 표시줄·트레이에 재사용한다. 설치 시 바탕화면 바로가기는 사용자가 선택한다.
- 네이티브 Windows 제목 표시줄을 사용한다. 브라우저 주소창은 표시하지 않는다.
- 단일 인스턴스만 실행한다. 두 번째 실행이나 정상 인증 콜백은 기존 창을 복원한다. 두 번째 공부 문서나 카메라 담당을 만들지 않는다.
- 창 위치·크기는 검증 후 저장하고, 모니터 구성이 바뀌어도 화면 안에서 복원한다.

### X와 트레이

- 트레이가 정상 생성된 뒤에만 X를 숨김으로 처리한다. 트레이 생성 실패 시 창을 유지하고 복구 가능한 오류를 표시한다.
- 최초 숨김 때 한 번만 “창을 닫아도 공부와 카메라는 계속됩니다. 트레이에서 다시 열 수 있습니다.”를 안내한다. 안내 확인 여부만 로컬에 저장한다.
- 트레이 메뉴는 `독서실 열기`, 비활성 상태 표시, 명시적 종료 메뉴로 최소화한다. 공부 제목·이메일 등 개인정보는 표시하지 않는다.
- 상태는 공부 중/휴식 중/대기 중, 이 PC 카메라 켜짐 여부, 연결 확인 필요를 구분한다. 오래된 snapshot을 정상 감시 중이라고 표시하지 않는다.
- 트레이 복원은 같은 문서를 보여 주기만 한다. 공부·카메라를 새로 시작하거나 다른 기기의 담당권을 가져오지 않는다.

### 완전 종료

트레이 종료는 기존 `deviceStudyActivity`에 해당하는 기기 단위 참여 상태와 미완료 저장을 기준으로 판단한다. 계정에 활성 세션이 있다는 이유만으로 다른 기기의 공부를 종료하지 않는다. 종료 직전에 현재 문서에 요청 ID가 있는 최신 상태 확인을 보내고 5초 안의 일치 응답을 사용한다. 주기 조회의 캐시만으로 종료하면 직전 공부 시작·저장 요청을 놓칠 수 있으므로 캐시만으로 완전 종료를 승인하지 않는다.

1. 이 PC가 유휴 관찰 기기이며 카메라·미완료 저장이 없으면 `앱 종료`로 종료한다.
2. 이 PC가 공부·휴식 세션에 참여하거나 카메라를 담당하면 `공부 종료 후 앱 종료`를 제공한다. 창을 복원하고 기존 웹 종료/회고/할 일 확인 흐름으로 보낸다.
3. 기존 서버 종료가 확인되고 로컬 카메라와 미완료 저장이 정리된 뒤 프로세스를 종료한다. 취소하면 앱은 계속 실행된다.
4. 연결 실패·웹 렌더러 장애로 종료를 확인할 수 없으면 재시도를 안내한다. 사용자가 별도 경고에서 선택한 `저장 확인 없이 앱 종료`는 프로세스만 종료하며, 서버 공부 종료를 성공으로 기록하거나 시간을 임의 보정하지 않는다.

Windows 종료·작업 관리자 강제 종료에는 정상 종료를 보장할 수 없다. 기존 서버 연결 유효 시간과 복구 정책을 따르며, 시작/종료 기록을 만들어 내지 않는다.

## 4. 숨겨진 창에서도 공부·카메라 유지

공부 BrowserWindow에 `backgroundThrottling: false`를 적용한다. X 처리에서 `destroy`, `webContents` 재생성, 페이지 이동, 카메라 stop을 실행하지 않는다. Chromium의 기본 숨김·최소화 스케줄링을 그대로 둔 채 카메라 유지가 된다고 가정하지 않는다.

이 설정만으로 수용 완료를 선언하지 않는다. 실제 Windows에서 창을 6분 이상 숨겨 다음을 함께 확인한다.

- 카메라 프레임·감지 평가가 계속 갱신된다.
- 담당 기기의 heartbeat와 서버의 신선한 감지 상태가 유지된다.
- 동일 계정의 웹/Android에서 공부 시간·휴식·재개·종료가 일치한다.
- 정상 착석 상태에서 숨김 때문에 추가 카메라 요청·5분 미감지 Slack 경고가 발생하지 않는다.

모의 영상 검증과 실제 웹캠 착석 검증은 별도 근거로 남긴다. 프레임 처리·기존 상반신 판정 조건·5분 경고·10분 제외 정책은 변경하지 않는다. 절전·연결 단절·카메라 고장 때는 기존의 연결 불명 처리와 복구를 사용한다.

## 5. 로그인과 동일 계정 기록

### 로그인

기존 공통 로그인 디자인을 사용한다. Google/GitHub는 시스템 브라우저 PKCE, 이메일은 기존 8자리 코드를 제공한다. 앱에서 한 번 로그인하면 탭 전환·창 숨김·복원·앱 재실행 시 같은 계정으로 연결한다. 일반 브라우저와 Windows 앱의 로그인 저장소는 별개이므로 최초 로그인은 필요하다.

Electron main이 Supabase Auth 클라이언트와 PKCE 검증자를 소유한다. 세션·검증자는 `safeStorage`로 암호화한 앱 전용 userData 경로에 저장한다. 암호화가 불가능하면 평문 저장으로 후퇴하지 않고 메모리 세션과 재로그인 안내를 사용한다. OS 사용자 권한을 가진 악성 코드에 대한 완전한 보호를 의미하지 않는다.

OAuth 콜백은 `studyroom-desktop://auth/callback`을 사용한다. main은 허용된 공급자 URL만 생성해 시스템 브라우저로 열고, 콜백의 정확한 scheme/host/path, 단일 code, 진행 중 인증 시도와 PKCE 교환을 검증한다. 취소·중복·지연·재실행 콜백을 처리하며 URL에 담긴 access/refresh token, 인증 시도 없는 콜백은 거부한다. 전체 실행 인자·콜백 URL·코드를 로그에 남기지 않는다.

이 콜백을 Supabase Auth redirect 허용 목록에 추가하는 운영 설정이 필요하다. 적용 직전에 대상·변경을 알리고 기존 웹·Android 허용 주소를 보존한다. OAuth 공급자 비밀키·기존 계정·요금제는 변경하지 않는다.

### 웹 세션 연결

기존 `mobile-web-auth` Edge 경로를 main에서 Bearer 인증으로 재사용한다. 현재 경로는 특정 플랫폼 헤더를 요구하지 않고, 검증된 같은 사용자에게 일회용 토큰 해시를 발급한다. 브라우저 CORS를 확대하지 않는다.

1. main에서 `auth.getUser()`로 현재 사용자를 검증한다.
2. 기존 발급 제한을 지키며 일회용 로그인 티켓을 요청한다.
3. 신뢰된 현재 최상위 문서에 요청 ID·인증 세대·기대 사용자·티켓만 전달한다. 장기 네이티브 토큰은 전달하지 않는다.
4. 웹의 별도 DesktopAuthGate가 티켓을 교환하고 사용자 일치를 검증한 뒤 기존 DashboardApp을 표시한다.
5. 로그아웃·계정 변경은 main과 웹을 함께 정리한다. 이전 계정의 늦은 티켓/응답으로 복원되지 않게 인증 세대를 검사한다.

웹에서 자체 생성한 세션은 전용 Chromium 저장소에서 유지한다. main의 refresh token을 웹 저장소에 복사하지 않는다. 기존 Android 연결 경로·일반 웹 로그인은 그대로 보존한다. 실제 티켓 발급/일회성 교환·로그아웃·재실행 검증이 실패하면 출시하지 않는다.

### 학습 데이터

기존 서버의 동일한 user_id/RLS/API를 사용한다. 공부·할 일·계획·목표·회복·팀·숲·기술 피드·설정 기록을 별도 복제하거나 병합하지 않는다. Windows 설치·업데이트·로그아웃은 서버 학습 기록을 삭제하지 않는다. 계정이 다른 두 기기의 데이터는 원래대로 분리된다.

## 6. 신뢰 경계와 권한

BrowserWindow는 `sandbox: true`, `contextIsolation: true`, `nodeIntegration: false`, `nodeIntegrationInSubFrames: false`, `webSecurity: true`로 생성한다. 개발 서버 허용은 개발 모드의 명시적 loopback 설정에만 한정하고 설치형에 포함하지 않는다.

- IPC는 정확한 production HTTPS origin, 현재 `mainFrame`, 문서 세대와 요청 ID를 모두 확인한다. 비동기 작업 후에도 다시 검증한다.
- preload는 버전/기능 조회, 제한된 인증 요청, 카메라 사전 안내, 기기 활동 snapshot, 종료 요청/결과만 노출한다. 임의 channel·URL·코드 실행·파일 경로 API는 노출하지 않는다.
- 카메라는 사용자의 명시적 버튼과 목적 안내 후, 신뢰된 최상위 문서의 video-only 요청만 허용한다. 권한 검사와 요청 handler를 모두 제한한다. audio·화면 캡처·위치·USB/HID·알 수 없는 권한은 거부한다.
- Windows 카메라 개인정보 설정에서 차단되면 안내와 안전한 설정 진입만 제공한다. 설정 복귀나 앱 진입 자체가 카메라/공부를 시작하지 않는다.
- 외부 링크는 검증된 HTTPS만 시스템 브라우저로 연다. remote 문서의 임의 navigation/new-window를 허용하지 않으며 `file:`, `javascript:`, `data:`와 임의 custom protocol은 차단한다.
- 영상·프레임·포즈 원본·마이크 음성은 네트워크나 문서·로그로 전송하지 않는다. 인증 정보·개인정보를 진단 자료에 기록하지 않는다.

## 7. 설정·설치·업데이트

기존 설정 탭에서 Windows 앱 버전과 빌드, X→트레이 동작, 카메라 권한 안내를 표시한다. Android 집중 모드·APK 업데이트 버튼을 Windows 네이티브 기능인 것처럼 표시하지 않는다. 공통 서버 설정과 일반 웹 화면은 기존 동작을 유지한다.

초기 Windows 버전은 `0.1.0`으로 별도 관리한다. Android `0.2.4`와 버전을 맞추거나 APK를 변경하지 않는다. 구현 시 지원 중인 Electron과 패키징 도구의 정확한 버전을 확인해 고정하고 lockfile에 반영한다.

- per-user NSIS x64 `.exe` 설치 파일을 만든다. 관리자 권한·Windows 자동 시작·시스템 절전 변경은 기본 요구하지 않는다.
- 로컬 설치→실행→업데이트 설치를 검증한다. 동일 앱 ID/userData 경로를 유지해 로그인 연결과 로컬 설정을 보존한다.
- 웹 변경은 기존 Vercel 배포를 통해 반영되지만, 실행 중 공부 화면을 강제 새로고침하지 않는다. 네이티브 변경은 새 설치 파일로 명시적으로 업데이트한다.
- 첫 버전에는 자체 자동 업데이트·백그라운드 설치를 추가하지 않는다. 공개 GitHub Windows Release와 고정 설치 링크 게시도 별도 출시 요청에서 진행한다.
- 코드 서명 인증서가 없으면 미서명 상태와 SmartScreen 안내를 명시한다. 인증서를 구매하거나 Windows 보호 기능을 끄지 않는다.

## 8. 실패 처리와 기록 보존

- 초기 연결 실패: 공통 톤의 재시도 화면을 표시하고, 다른 서버나 임의 계정으로 접속하지 않는다.
- 공부 중 통신 실패: 기존 마지막 확인 상태와 연결 확인 필요를 표시한다. 서버 승인 없이 공부/출석 성공을 꾸미지 않는다.
- renderer crash: native 창은 오류·복원 경로를 제공한다. 복원 시 서버 최신 상태를 확인하고 카메라 담당 계약을 지킨다. 카메라와 공부를 임의 새로 시작하지 않는다.
- 오래된 웹/브리지 버전: capability 협상으로 지원하지 않는 버튼을 숨기고 명시적 호환 오류를 표시한다. 무반응 버튼을 제공하지 않는다.
- 테스트 항목은 `[테스트] Windows ...`로 식별한다. 기존 회복 루틴을 대리 제출하거나 학습 기록을 삭제·초기화하지 않는다. 새 검증 학습 기록은 근거로 보존하고 임시 할 일만 식별해서 정리한다.

## 9. 완료 기준과 검증 순서

### 자동 검증

- 신규 desktop 정책/생명주기/인증 단위 테스트: URL·frame·권한 차단, X→hide, 단일 인스턴스, 트레이 실패, 종료 취소/저장 실패, 늦은 인증 응답.
- 실제 Electron 통합 테스트: BrowserWindow 숨김/복원·renderer 유지·영상 프레임 진행·IPC 차단·종료 흐름. mock 테스트만으로 대체하지 않는다.
- 웹 mounted 회귀: 일반 웹/Android/Windows 인증 분기, 로그아웃, 기기 단위 종료, 기존 카메라·다중 기기 동기화.
- root에 `desktop:check`, `desktop:test`, `desktop:build`를 추가하고 Dune 검증 목록에 연결한다. 세부 명령은 승인 후 구현 계획에서 확정한다.
- 기존 `npm.cmd test`, `npm.cmd run test:edge`, `npm.cmd run mobile:check`, `npm.cmd run build`, `npm.cmd run docs:check`, `ai.ps1 verify --project <root>`, `git diff --check`를 통과한다.

### Windows 실제 수용

1. 설치·단일 실행·기존 공통 UI·각 탭·8자리/Google/GitHub 로그인·로그아웃·재실행을 확인한다. 외부 계정 인증은 사용자가 안전하게 직접 수행한다.
2. `[테스트]` 할 일로 기존 공부 시작·휴식·재개·종료/회고를 수행하고 서버 값과 대조한다. 실제 회복 잠금은 우회하지 않는다.
3. 같은 계정의 웹과 Android 16 앱에서 시간·할 일·카메라 담당·상태가 일치하고, 관찰 기기에 추가 카메라 인증이 없는지 확인한다.
4. 창을 6분 이상 숨겨 실제 웹캠 감지·heartbeat·잘못된 Slack 경고가 없는지 검증한다. 자동 영상 fixture와 실제 착석 수용을 구분한다.
5. 트레이 복원/완전 종료 취소·성공/다른 기기 공부 중 종료/연결 실패·복구/강제 종료 후 재실행을 확인한다.
6. 375px·1440px 및 Windows 배율 125%/150%, 키보드 포커스·대비·터치 영역을 기존 화면과 비교한다.
7. 같은 설치 파일 계열의 업데이트 설치 후 로그인·설정·서버 기록을 확인한다. 기존 행 count/digest와 새 테스트 행을 구분해 보존을 검증한다.

독립 `shared-reviewer` 검토를 받고 차단 결함을 해결한다. 웹 브리지가 바뀌면 프로젝트 지침의 기능 브랜치 커밋·Vercel production READY/exact SHA/HTTP 200까지 확인한다. 로컬 설치 성공, 운영 웹 배포, 공개 Windows 설치 파일 게시, 실제 웹캠 수용을 각각 구분해 보고한다.
