# 관심 내용 기반 기술 피드 — 설계 검토안

날짜: 2026-09-12
상태: 사용자 승인된 방향을 구체화한 설계. 아직 코드/운영에 적용하지 않음.
관련 PRD: memory-bank/prd-tech-feed.md

> [!IMPORTANT]
> **대체된 역사적 설계안:** 아래 내용은 구현 전 RSS/API 선별 방향을 기록한 문서입니다. 현재 구현 기준은 [web-search-spec.md](./web-search-spec.md)이며, 공개 기술 관심 입력은 3–300자이고 앱 소유 검색 제공자를 통한 공개 웹 검색을 포함합니다.

## 목적

사용자는 독서실 웹에서 원하는 기술을 입력하고 "소식 받아보기"를 누른다. 외부 계정 연동, API 키 입력, 운영자의 계정별 수동 등록 없이 시작/수정/중지한다.
운영자가 수집 기반을 준비하는 일과 사용자가 관심사를 설정하는 일을 분리한다. 화면만 배포하고 기사가 없는 상태를 출시 완료로 보고하지 않는다.

## 구현 범위와 경계

- 이번 범위는 기존 공개 RSS/Atom/Hacker News API에서 수집한 글을 관심 내용에 맞게 선별하는 방식이다.
- 자유 입력을 지원하되, 웹 전체 검색이나 모든 기술에 대한 결과를 보장하지 않는다. 화면에 "공개 기술 소스에서 관련 소식을 모아요"라고 설명한다.
- 일반 웹 검색은 별도 검색 공급자/운영 키/요금·데이터 이용 조건을 결정한 뒤 확장한다. 이번 단계에서 검색했다고 표시하거나 AI가 지어낸 기사를 넣지 않는다.
- RSS/API 수집, 중복 방지, 보안 전송, 저장/할 일 연결, 무료 AI 요약을 재사용한다.
- 기존 source 구독 기능은 "고급 설정: 수집 출처"로 이동한다.
- SNS OAuth, 비공개 자료, 유료 AI, Expo 피드 화면은 이번 범위가 아니다.
- 현재 수집 서비스는 꺼져 있고 소스8개 승인 대기/기사0건이다. 구현 완료와 실제 가동 완료를 구분한다.

## 사용자 흐름

1. 기술 피드 첫 방문: 관심 내용 입력창, 예시 세 개, 소식 받아보기 버튼을 보여준다.
   - 예시: "AI 에이전트와 LLM", "AWS와 클라우드", "파이썬 백엔드".
2. 입력은 최대500자. 서버가 관심 키워드를 제안하고 화면에 수정 가능한 태그로 보여준다.
3. 뜻이 분명한 입력은 한 번의 시작 동작으로 저장한다. 해석이 불확실하면 시작하지 않고 태그 확인을 요청한다. 임의로 광범위한 분야를 구독하지 않는다.
4. 시작 후 상태는 "수집 대기 / 소식 업데이트됨 / 관련 소식 없음 / 일시 중지 / 서비스 점검 중"으로 구분한다.
5. 설정 변경·일시 중지는 같은 화면에서 한다. 일시 중지해도 저장한 글과 할 일 연결은 보존한다.
6. 로그인 계정에 설정을 저장하고 다른 기기에서 동일하게 복원한다. 계정 전환 시 이전 관심 내용과 글을 즉시 비운다.
7. 이용자별 운영 승인을 요구하지 않는 self-service 모드를 제공하되, 서버 전체 중지 스위치는 유지한다.
8. 운영 서비스가 꺼져 있어도 관심 설정은 저장할 수 있다. "설정은 저장됐어요. 현재 새 소식 수집은 준비 중이에요"라고 표시한다. 가동되지 않았는데 수집 중이라고 말하지 않는다.

## 키워드 해석과 관련성

- 새 순수 모듈 tech-feed-topics.mjs: normalizeTopicInput, proposeTopics, validateTopicSelection.
- 의미 단위 최대10개, 태그별 최대60자. 영어 대소문자/여백/NFKC 정규화. 제어문자·URL·이메일·명백한 토큰 입력은 거절하고 공개 기술 관심사만 입력하도록 안내.
- 기본 사전: AI/인공지능, AI agent/AI 에이전트, LLM/대규모 언어 모델, AWS/아마존 웹 서비스, Python/파이썬, backend/백엔드, frontend/프론트엔드, React, Kubernetes/쿠버네티스, Docker/도커.
- 알려진 사전 항목은 명확한 동의어만 확장한다. 미등록 기술명도 사용자가 태그로 확정하면 그대로 검색어로 저장한다.
- "AI 제외", "AWS 말고" 같은 부정/복합 조건은 첫 버전에서 추측 처리하지 않고 "포함할 키워드를 확인해 주세요"로 태그 확인 단계로 이동한다.
- 기본 관련성은 제목·출처 소개의 단어/구문 일치다. AI가 없는 경우에도 작동해야 한다. AI/Go/R처럼 짧은 영어는 단어 경계를 적용한다.
- 태그 간 OR, 같은 태그의 여러 단어는 구문으로 취급한다. 광범위 분야만 일치하는 글을 세부 기술 일치로 포장하지 않는다.
- AI 요약은 관련 글에 한정한다. 기존 무료6회/사용자/일 공유 한도(실패 포함)를 유지하고 요약 성공 결과는 재사용한다.
- AI 해석을 도입할 때도 태그 응답을 검증하고 제안으로만 사용한다. 이번 기본 시작 흐름은 AI 호출 성공에 의존하지 않는다.
- 카드에 "Python 관련"처럼 실제 일치한 태그를 표시한다. 근거가 없는 추천 이유는 생성하지 않는다.

## 데이터와 API

기존 tech_feed_preferences에 추가형 마이그레이션:
- topic_prompt text: 기본빈값, 최대500자.
- topic_terms jsonb: 기본[], 각 항목 {label:string, aliases:string[]} 최대10개/각 alias 최대60자/항목별 alias 최대6개.
- receiving boolean: 기본false.
- topic_revision bigint: 기본0, 설정을 저장할 때 증가.
- updated_at timestamptz.
기존 interests는 호환 필터로 유지한다. 기존 사용자는 자동 opt-in하지 않는다.

기존 subscriptions는 그대로 유지:
- 추가 subscription_mode: manual|automatic, 기존 행은 manual.
- 최초 시작 때 승인된 추천 소스를 automatic으로 연결한다. 공통 수집 후 관심 태그로 글을 선별한다.
- 고급 설정에서 사용자가 명시적으로 끈 소스는 manual/subscribed=false로 유지하고 관심 내용 수정 시 다시 켜지 않는다.
- 새 승인 소스는 receiving 사용자의 자동 소스 후보가 될 수 있지만 사용자별 수동 제외는 존중한다.
- 개인 관심 내용은 다른 사용자에게 노출하지 않으며 원문 사이트로 전달하지 않는다.

인증 API 추가:
- topics_preview {prompt} → {terms, needs_confirmation, explanation}; deterministic, 외부 AI 호출 없음.
- topics_save {prompt, terms, receiving, expected_revision} → {preferences, collection_state}; 원자적 변경/중복 클릭 안전. owner는 인증 토큰에서만 얻는다.
- receiving {receiving, expected_revision} → {preferences}; true는 저장된 유효 태그가 있어야 함.
- state → 기존필드 + preferences + service_available + collection_state.
- list → 기존페이지 + matched_topics, topic_revision. latest는 관심 일치 필터 적용 후20개 커서페이지; saved는 관심 변경/수신중지에도 기존 저장글을 유지.
- 오래된 revision 요청은409와 최신 설정 재로드 안내. 여러 기기의 수정 덮어쓰기를 조용히 허용하지 않는다.
- 기존 timezone action은 모든 피드/receiving 플래그와 독립 유지.

## 수집과 권한

- 서비스 모드: pilot/self_service. 기존 pilot은 롤백용, 운영 가동 완료 후 self_service에서 인증된 일반 사용자가 웹에서 직접 시작한다.
- global switch는 수집/요약을 중지한다. state/preferences/timezone 접근은 유지한다.
- worker가 서비스 대상이며 receiving=true인 계정의 구독만 수집 대상으로 삼는다. 사용자 수만큼 동일 URL을 요청하지 않는다.
- receiving=false 사용자는 새 AI 호출의 비용 주체가 될 수 없다. 공유 소스는 다른 receiving 사용자가 있으면 계속 수집될 수 있음을 구분한다.
- 함수/조회는 service-only 쓰기와 owner RLS를 유지한다. 관심 필터는 SQL 페이지 제한 전에 적용한다. 클라이언트에서20개를 받은 뒤 필터링하지 않는다.
- 사용자 입력을 SQL 문자열/정규식/프롬프트 명령으로 연결하지 않는다. 정규식은 서버가 이스케이프한 alias에만 사용하며 경계/길이 제한을 테스트한다.
- 기존 HTTP DNS/TLS 고정, 리디렉션/XXE/응답 크기 제한을 약화하지 않는다.
- 아직 모르는 출처의 이용 조건을 임의 승인하지 않는다.

## 운영 가동 기준

- 소스별 수집/소개 저장/AI 요약 허용 범위를 실제 근거로 검토하고, 허용되는 범위만 켠다.
- 최소 한 개의 실제 사용 가능한 승인 소스가 있고 실제 기사가 저장되어야 출시 완료라고 보고한다.
- 수집 전용 비밀키와 Vault/예약 요청을 연결하고, worker 인핸들러 인증의 무키/오키401와 정상 인증 실행을 검증한다.
- 신규 함수 JWT 설정 변경이 필요하면 변경 목적과 남는 인증을 설명하고 승인받는다. 현재 설정을 조용히 낮추지 않는다.
- 실제 사용자 세션으로 state/설정 저장/list/시간대 정상 응답을 확인한다. gateway401만으로 완료라고 하지 않는다.
- 기존 출석 Cron을 건드리지 않는다. 피드 Cron만 마지막에 활성화한다.
- 브라우저 종료 후 예약 실행 두 회 성공과, 실제 시간별 재수집/중복 방지는 실행 시각과 소스 run_after로 별도 확인한다.
- 무료 AI 설정이 없으면 소개 기반으로 출시 가능하며 AI가 요약했다고 표시하지 않는다.

## 완료 기준

- PC와390px 모바일에서 관심내용 입력→시작→맞춤 글→저장/할 일 흐름.
- 계정별 opt-in/일시중지/다른 기기 복원/동시수정 충돌/계정 전환 격리.
- API 입력검증, 실제 SQL 필터링/페이지20/저장 보존/worker opt-in/쿼터 회귀.
- Node 전체, Deno Edge 검사와 배포 그래프 회귀, 웹 빌드, 모바일/README 검사.
- 소스 범위와 운영 가동 여부를 UI/문서/최종 보고에서 정확하게 구분.

## 확인할 설계 경계

이 설계의 첫 버전은 "공개 기술 소스에서 관심사에 맞게 선별"이다. "입력한 주제로 웹 전체를 검색"까지 첫 버전에 포함하려면 검색 공급자/비용/출처 정책을 추가 확정해야 한다. 이 경계 확인 전 코드를 구현하거나 운영 설정을 변경하지 않는다.
